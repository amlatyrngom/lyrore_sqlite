# Generalizable Lessons from SQLite Step 1

## Critical: Recursion Guard for Nested Database Connections

**Problem:** When SQLite initialization code opens another database connection (e.g., for state persistence), it triggers the same initialization path → infinite recursion → stack overflow.

**Pattern:** Use a static guard flag:
```c
static int lyroreInitializing = 0;

int lyroreInit(sqlite3 *db){
    if(lyroreInitializing) return SQLITE_OK;  // Already in init
    lyroreInitializing = 1;
    // ... open state connection via sqlite3_open_v2() ...
    lyroreInitializing = 0;
    return SQLITE_OK;
}
```

**Applies to:** Any extension that opens auxiliary connections during init.

## Critical: Out-of-Tree Builds for SQLite

**Problem:** Building in-tree pollutes source directory with ~50+ generated files, making `git diff` useless and patches unreliable.

**Pattern:** Always build out-of-tree:
```bash
mkdir -p ~/sqlite_build && cd ~/sqlite_build
/path/to/sqlite/configure
make -j4 "OPTS=-DSQLITE_ENABLE_LYRORE=1"
```

**Why it matters:**
- Clean `git status` shows only source changes
- Patches contain only intentional modifications
- No risk of accidentally committing build artifacts

---

## SQLite Build System: Amalgamation Awareness

**Problem:** Adding files to `main.mk` alone is insufficient. SQLite's release build uses `sqlite3.c` amalgamation generated by `tool/mksqlite3c.tcl`.

**Pattern:** When adding new source files:
1. Add to `main.mk` (LIBOBJS0)
2. Add headers to `available_hdr` in `mksqlite3c.tcl`
3. Add sources to `foreach file` section in `mksqlite3c.tcl`

## What Worked Well

**Dual testing approach:** Both TCL tests (SQLite's native format) and C API tests. TCL tests integrate with SQLite's test harness; C tests verify programmatic API correctness.

**Planning phase first:** A dedicated planning sub-agent identified exact line numbers and integration points before any code was written. This prevented wasted iterations.

**Dedicated state connection:** Using a separate database connection for Lyrore's internal state avoids transaction conflicts with user queries - design was correct as specified.

---

## Anti-Pattern: Cleanup Agent Scope

**Learned:** When cleaning build artifacts, verify against the intended deliverables (e.g., the diff file) before deleting files. The cleanup agent accidentally removed a test file that looked like a build artifact.

**Prevention:** Have cleanup operations explicitly preserve files matching patterns in the deliverable set.
